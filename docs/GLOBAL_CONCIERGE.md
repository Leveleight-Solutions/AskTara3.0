# Global concierge

Asktara can research destinations beyond the featured Explore collection when OpenAI is connected. The catalog remains an editorial starting point. A named city is resolved from current web sources; it is never silently replaced with a catalog suggestion. Ambiguous or unsupported research asks for clarification and preserves an existing saved itinerary.

The workflow in [server/agents](../server/agents/) separates four conversational intents: creating or changing a plan, discovering possible destinations, answering a question about the current plan, and requesting clarification. Planning uses four model stages: **intake → live research → operating-status verification → composition**. Intake preserves supplied dates, party size, route order and preferences. Research uses the Responses `web_search` tool and accepts evidence links only from returned search sources. After all optional Google/place enrichment and supplier stages finish, a separate forced-web verifier checks venue identity and current closure notices against the trip dates. Composition then selects from the retained researched places; deterministic scheduling checks day allocation, duplicates, timing, protected stops and estimated group costs. Supplier rates remain separate from web evidence.

The [operating-status verifier](../server/agents/verify.ts) excludes places with sourced closure notices overlapping the trip from new suggestions and destination highlights. Protected saved appointments remain in their original schedule with a specific warning, so the traveler can unlock, remove or replace them. Missing verification coverage or unclear dates produce uncertainty notes. “No closure notice found” means exactly that; it does not establish that a venue is open, bookable, accessible or suitable for a particular diet. Running verification after enrichment prevents a later place source from reintroducing an excluded venue before composition.

Answer requests receive the saved itinerary, place records and source references. They can compare existing choices and search for updated supporting information while preserving the actual schedule, dates, duration, party and budget. Existing evidence links are research leads; newly stated factual claims still require current search evidence. An answer must distinguish saved stops from fresh recommendations.

Research snapshots belong to the trip through `Trip.destinations` and its planning report, rather than a mutable global catalog. Shared destination fields contain public city information. Personal requirements belong in the private brief and suitability notes. Snapshot-aware lookup supports trip cards, route settings, maps, saved revisions, shared itineraries and copies. Client edits cannot introduce arbitrary destination snapshots. Hotel searches can send an owned `tripId` so the backend resolves researched destination coordinates from that trip.

Planning runs expose progress, cancellation and retry with request-ID deduplication. The browser renders progress from run events, so the `verification` agent automatically appears as “Checking venue status” without a separate hardcoded UI stage list. Saved trips, sessions and revisions use SQLite. Restart recovery, ownership checks and optimistic revision checks remain part of the existing application; deployment requires the persistent single-instance arrangement described in [Railway deployment](RAILWAY_DEPLOYMENT.md).

| Setting                                    | Purpose                                                                                                                                |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| `OPENAI_API_KEY`                           | Server-side intake, web research, operating-status verification and composition. Both web-search stages use this same key.             |
| `OPENAI_MODEL` / `OPENAI_REASONING_EFFORT` | Current defaults: `gpt-6-astra` / `low`. The account must support the selected model and tools.                                        |
| `LITEAPI_API_KEY` / `LITEAPI_MODE`         | Hotel and flight rate searches. The current development credential is sandbox and uses `test`; simulated rates remain visibly labeled. |
| `DUFFEL_ACCESS_TOKEN`                      | Optional alternative flight provider; takes precedence over LiteAPI for flights.                                                       |
| `GOOGLE_PLACES_API_KEY`                    | Optional fresh Google place details. Separate from web research evidence.                                                              |
| `GOOGLE_MAPS_EMBED_API_KEY`                | Separate public, restricted browser embed key. External Google Maps links also work without an embed key.                              |

Keep provider secrets on the server. `LITEAPI_PUBLIC_KEY` is not consumed by the current search adapters. Configuration flags only indicate presence; working model permissions, supplier access and inventory require successful requests. See [integration details](INTEGRATIONS.md).

The UI renders source-linked paragraphs and lists without executing HTML or unsafe URL schemes. Research timestamps indicate when information was checked, not future opening hours or availability. Place details expose evidence and suitability notes. Dietary requirements, step-free access and quietness still require direct venue or transport confirmation; a source link is not a guarantee. The neutral destination illustration is a fallback, not a destination photograph.

Initial research and the separate operating-status verifier each have a maximum of four search calls and bounded place records. This provides a practical starting itinerary, not exhaustive destination coverage or universal status verification. Activity costs and travel times are estimates; missing supplier results do not mean sold out. The planning agents do not book or pay. A separate [sandbox checkout](BOOKING_WORKFLOW.md) implements explicit hotel confirmation and cancellation; production payments and flight ticket issuance remain unverified. Visa/passport advice is not inferred from hotel guest-nationality fields.

Focused regression coverage includes `tests/global-workflow.test.ts`, `tests/openai-research.test.ts`, `tests/place-verification.test.ts`, `tests/global-hotels.test.ts`, `tests/research-ui.test.ts` and `tests/itinerary-map.test.ts`. Verification tests cover sourced closures, protected stops, uncertainty and invalid evidence. The mocked browser journey in `tests/research-ui.spec.ts` checks non-catalog Osaka/Nara snapshots, Markdown sources, maps, settings, hotel trip context, sharing/copying and mobile layout. It does not establish live supplier availability.

`tests/london-ui.spec.ts` uses the actual API and any configured model. It exercises the exact London request, then switches to a six-day Osaka itinerary when global AI research is connected; both live plans must complete the verification agent and retain its completion in the saved report. Without AI, it verifies that an unsupported-city request preserves the London plan. It reloads saved state and deletes only its synthetic trip. These real model requests consume the configured account's quota; no flight or hotel search is requested by this journey.

On 12 September 2026, a live `gpt-6-astra` follow-up on a saved synthetic three-day Osaka plan completed in 31.5 seconds. It discussed the actual saved OPTIMUS cafe and Nakanoshima Park stops, cited web sources and distinguished an unscheduled researched attraction. The serialized itinerary, destination, dates, duration, travelers and budget were unchanged; hotel, flight and scheduling stages were skipped. The check ran directly on a copied workflow input, without changing a database or deployed trip.

That answer also caught a stale cafe choice in the earlier fixture, generated before the separate verifier existed: the [official OPTIMUS cafe page](https://www.optimus-cafe.com/english.html) announces closure on 25 March 2026, despite retaining old menu and opening-hour sections. The closure precedes the fixture's November trip. This finding became a regression requirement for the new forced-web verification stage: current closure notices take precedence over older menus and hours, known-closed choices are excluded from new suggestions, and protected appointments are retained with warnings. Two subsequent real GPT-6 Astra closure checks passed: they excluded the cafe using its official notice and retained the park candidates. Automated regressions cover the same behavior, including protected appointments. The earlier answer check remains evidence of cited answers and exact schedule preservation, not evidence that initial planning had already verified operating status.
