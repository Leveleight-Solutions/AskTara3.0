# Asktara integrations and credentials

Research date: 11 September 2026. The recommendations below come from official documentation. Account access, quotas, commercial terms, and country eligibility must be confirmed with the provider for the business that will operate Asktara.

The current build includes AI planning, supplier search and sandbox checkout. Hotel prebook, no-charge sandbox confirmation, retrieval and cancellation use the existing LiteAPI key. Flight verification is enabled separately from confirmation, which remains off until the account's payment capability is verified. Production booking and payment are disabled. See [booking implementation and limits](BOOKING_WORKFLOW.md). Configure secrets through the local environment file or hosting secret store.

Asktara now implements a coordinated workflow with separate structured OpenAI intake, required web-search research, independent venue-status checks and composition calls. Native server tools perform places, hotel, and flight research when configured and when the traveler supplies the required fields. Scheduling, source validation, protected-stop preservation, budget review, and persistence remain application-controlled. This is not an unrestricted tool-calling loop or an implementation of Odessia's private agents. [OpenAI structured-output documentation](https://developers.openai.com/api/docs/guides/structured-outputs), [Asktara architecture](PLANNING_ARCHITECTURE.md)

Without keys, the same run lifecycle works with clearly labeled curated planning. Add keys in `.env` and restart the backend. Supplier secrets stay server-side; the optional map uses its own public, website-restricted Embed key. In trip settings, enable hotel/flight research and supply exact dates, nationality, and airport codes as applicable. Hotel/flight lookup is search only; the plan does not reserve inventory. The pipeline reports missing inputs and provider failures instead of inventing results.

Duffel live activation requires email and business/personal verification. Its payment product is country-dependent; the official onboarding flow also describes using a funded Duffel balance when not using Duffel Payments. Confirm the business's supported setup before promising in-app flight purchases. A future alternative to custom checkout is Duffel's hosted Links flow; it still requires integration and an eligible account. [Getting started](https://duffel.com/guides/getting-started), [Duffel Links](https://duffel.com/docs/guides/duffel-links)

Provider fallbacks: Mapbox Search Box is an alternative for place/address/POI search, subject to its geography and data-use limits. GetYourGuide is an alternative activity supplier, but its public criteria currently set substantial traffic/download thresholds for API access; availability/booking require higher levels. These are alternatives to evaluate, not preconfigured adapters. [Mapbox Search Box](https://docs.mapbox.com/api/search/search-box/), [GetYourGuide access requirements](https://partner.getyourguide.support/hc/en-us/articles/13981133907613-API-integration-and-requirements)

Curated destination data, private saved trips, saved inspiration added to an existing itinerary, account-scoped preferences, account management, a downloadable `.ics` calendar file, and a shareable plan page do not intrinsically require paid travel APIs. Direct calendar synchronization would be a separate OAuth integration; calendar export alone does not require it. The local build uses a persistent SQLite database for a single application instance. Forgotten-password recovery and email verification are not implemented. A signed-in user can change their password by supplying the current password, revoke other sessions, download their data, and delete their account with password confirmation. Profile defaults are stored by owner; existing account preferences take precedence over guest choices on sign-in. Deployment, durable backups, and any move to a shared database require separate production work.

Infrastructure environment settings are `PORT`, `DATABASE_PATH`, `APP_ORIGIN`, `TRUST_PROXY`, and `COOKIE_SECURE`; these are application settings, not supplier keys. Use the checked-in environment example and README for their actual supported values. The default AI model is `gpt-6-astra`; `OPENAI_MODEL` can select another supported model compatible with the implemented Responses request.

## Features that work without provider keys

`GET/PATCH /api/profile` saves pace, interests, home airport, nationality, dietary/accessibility selections and planning notes for the current owner. Dietary selections use a defined set (vegetarian, vegan, gluten-free, dairy-free, nut/shellfish allergy, halal and kosher); access selections cover wheelchair/step-free access, elevators, ground-floor rooms and accessible bathrooms. These populate the trip brief and an unverified-requirements review warning. They do not certify or filter suppliers for verified allergy or accessibility suitability. Freeform planning notes are limited to 500 characters; the trip editor supports up to 12 notes of 500 characters each. New planning runs use these backend defaults, and explicit trip inputs take precedence. `GET/PATCH /api/account`, password/session endpoints, JSON export and confirmed account deletion are implemented using the local database and existing secure sessions. No provider request is needed for these operations.

`POST /api/trips/:id/items` adds a catalog stay idea or experience to a selected day with owner, destination, time-overlap and revision checks. The server resolves trusted catalog content, marks the stop protected and deduplicates retries by request ID. Catalog entries remain inspiration; this endpoint creates no supplier reservation.

## Supplier adapter details

### Duffel search

- `POST https://api.duffel.com/air/offer_requests`
- Headers: `Authorization: Bearer <token>`, `Duffel-Version: v2`, and JSON content/accept headers.
- Body contains `data.slices` with origin, destination, departure date; `data.passengers`; optional cabin/filter fields. A return journey uses two slices.
- Duffel adapter retains all journey slices and segments, original provider currency/total, carrier details, expiry and passenger baggage when supplied. Detail panels show the complete outbound and return itinerary, preserve local airport times and identify missing or expired quotes. Test/live status remains visible. Recheck offers before any future purchase flow. [Official endpoint](https://duffel.com/docs/api/offer-requests/create-offer-request)

### LiteAPI search

- `POST https://api.liteapi.travel/v3.0/hotels/rates`, header `X-API-Key`.
- Requires `checkin`, `checkout`, `currency`, `guestNationality`, `occupancies`, and a location method such as `cityName` + `countryCode` or hotel IDs.
- For hotel-ID searches, `includeHotelData: true` includes names/photos. `maxRatesPerHotel: 1` is useful for result lists. Preserve currency, exact rate terms, and supplier identifiers.
- Rates are in `data[].roomTypes[].rates[].retailRate.total[0]`; join top-level `hotels[].id` to `data[].hotelId` for included hotel metadata. Respect the response's `sandbox` flag. Official documentation identifies `sandbox_`/`sand_` test keys and `prod_` production keys. The UI explicitly marks test rates and otherwise describes provider rates. [Official response examples](https://docs.liteapi.travel/reference/prompt-for-vibe-coding-tools)
- `LITEAPI_MODE` can be `provider` (conservative default), `test`, or `live`; set `live` only for a confirmed production account. An explicit sandbox response or sandbox key must always retain its test label.
- Hotel checkout implements search → prebook → explicit confirmation → book, with retrieval and cancellation. Sandbox uses `ACC_CREDIT_CARD` and creates test reservations only; no payment key or card number is required for this flow. [Rates reference](https://docs.liteapi.travel/reference/post_hotels-rates), [sandbox booking contract](https://docs.liteapi.travel/reference/post_rates-book)

### LiteAPI flight search

- `POST https://api.liteapi.travel/v3.0/flights/rates`, header `X-API-Key`.
- Body includes `legs` with `origin`, `destination`, and `date`, plus cabin/adult and `currency`. For round trips, provide both outbound and inbound legs.
- The same `LITEAPI_API_KEY` used for hotels is used for flights; one key covers both when a supported LiteAPI account is enabled.
- Responses return leg/journey objects; the adapter normalizes those into the existing `FlightOffer` + journey/segment model used by the UI and marks source as `LiteAPI` with provider environment status `test|live|unverified`.

## Booking completion criteria

Sandbox checkout now collects required guest details, revalidates quotes, displays terms and changed prices, requires explicit confirmation, persists supplier references and prevents duplicate dispatch. Hotel confirmation/status/cancellation are tested. Flight confirmation is guarded by `LITEAPI_FLIGHT_BOOKING_ENABLED=false` until sandbox credit/payment-bypass access is verified. Production activation still requires a verified payment workflow, supplier servicing and recovery procedures; the existing public key alone does not supply those capabilities. See [booking workflow](BOOKING_WORKFLOW.md) and [flight research](FLIGHT_BOOKING_RESEARCH.md).

Keep all supplier secrets server-side. Distinguish curated inspiration, sandbox offers, live search results, and confirmed bookings throughout the UI. Provider errors and missing credentials must not fall back to invented live prices or confirmations.

### OpenAI global research

The existing `OPENAI_API_KEY` also authorizes the Responses `web_search` tool. No separate search API key is needed. `OPENAI_MODEL=gpt-6-astra` selects the requested model; `OPENAI_REASONING_EFFORT=low` is the default reasoning level. Source URLs and research timestamps accompany suggestions, and only URLs returned by actual web-search output can support place records. Research provides destination and venue evidence, not supplier availability or guaranteed future opening hours. [Official web search guide](https://developers.openai.com/api/docs/guides/tools-web-search)

The configured LiteAPI sandbox key intentionally remains shared by hotel and flight searches while development continues. `LITEAPI_PUBLIC_KEY` is not used by the current server search adapters. Production booking requires separate implementation and supplier activation; a public key alone does not create a checkout flow.

### Google Places planning research

- `POST https://places.googleapis.com/v1/places:searchText` with `X-Goog-Api-Key` and an explicit `X-Goog-FieldMask`.
- The request combines a resolved destination, interests, a location bias, and a bounded result count. The adapter discards closed businesses and distant results.
- The engine records provider provenance, published hours, and a map link. No reviews, ratings, or photo assets are copied. User-visible stop costs and visit durations remain planning estimates.
- Published weekly hours do not validate opening on a future holiday or confirm availability. Travel-time allowances are not Routes API results.
- Google research content is stripped before saving trip, run, and revision JSON. Place IDs and application-authored allowances remain; owned place-detail reads fetch fresh provider content with no-store responses. The frontend holds the fresh names, addresses, and hours in page state only. Review any future storage or map changes against the [official Places policies](https://developers.google.com/maps/documentation/places/web-service/policies).

### Google Maps itinerary display

Set `GOOGLE_MAPS_EMBED_API_KEY` to a **separate public browser key**. Enable Maps Embed API in its Google Cloud project and meet the provider's account/billing prerequisites. Apply an API restriction allowing **Maps Embed API only**, then a **Websites (HTTP referrers)** application restriction allowing the exact Asktara development/production origins, for example `http://localhost:5173/*` and `https://your-asktara-domain.example/*`. Do not authorize arbitrary websites or reuse `GOOGLE_PLACES_API_KEY`. Google recommends separate restricted Embed keys. [Setup](https://developers.google.com/maps/documentation/embed/get-api-key), [security guidance](https://developers.google.com/maps/api-security-best-practices)

`GET /api/config` explicitly exposes only this public Embed key. Server secrets are never included; a value identical to a configured server provider key is withheld. The iframe uses the fixed `https://www.google.com/maps/embed/v1/` endpoint, encoded parameters and `referrerPolicy="strict-origin-when-cross-origin"`. Google receives the app origin for key validation without the private trip path. The app's content policy allows frames from `https://www.google.com`; Google's map controls, attribution and branding remain intact. [Embedding and referrer policy](https://developers.google.com/maps/documentation/embed/embedding-map)

The map follows the selected day's known catalog landmarks and researched Google place IDs. Fresh Google labels are supplied from transient page state; the map adds no durable provider data. Flexible itinerary blocks and fictional sample stays are excluded from map pins. Map directions are for review and do not rewrite the schedule's estimated travel allowances.

Without the Embed key, travelers can open real Google Maps routes/place links. Routes preserve place IDs when available and split long or mixed waypoint groups into mobile-compatible sections; Google Maps URLs need no key and allow at most three intermediate waypoints on mobile browsers. A fallback link remains visible when a configured embedded map cannot load; live Embed rendering must be checked with the restricted key on the intended origin. [Maps URLs](https://developers.google.com/maps/documentation/urls/get-started)
